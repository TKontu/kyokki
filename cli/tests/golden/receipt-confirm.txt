usage: kyokki receipt confirm [-h] --all-matched [--assign LINE=PRODUCT_ID]
                              [--new LINE=CATEGORY] [--skip-unmatched]
                              [--purchase-date YYYY-MM-DD] [--dry-run]
                              [--url URL] [--token TOKEN] [--json] [--verbose]
                              ID

Confirm receipt ID: send every line with a matched product, using
its own quantity and unit, and the receipt's purchase date (or
--purchase-date, required when the receipt has none). Non-food lines are
never stocked. Confirm is final: a line not sent is never stocked.

If any food line is unmatched, this refuses (exit 6) and lists them. Fix
them with --assign (an existing product) or --new (a new one), both
repeatable, or leave them out with --skip-unmatched. The receipt must be
read (not still processing, failed, or already confirmed), also exit 6.
--dry-run prints exactly what would be sent and sends nothing. The
confirm endpoint has no Idempotency-Key, so a retried confirm answers
from the server instead of replaying: 409 (already confirmed) is exit 6,
400 (the request was rejected, e.g. a since-deleted product id; re-run
receipt status) is exit 2.

positional arguments:
  ID                    the receipt's id (a UUID), from receipt upload

options:
  -h, --help            show this help message and exit
  --all-matched         confirm every matched food line (the only mode there
                        is today)
  --assign LINE=PRODUCT_ID
                        attach line LINE (as receipt status numbers it) to an
                        existing product; counts as matched; repeatable
  --new LINE=CATEGORY   create a new product for line LINE, named by its
                        generic name (the printed name if it has none), in
                        CATEGORY; counts as matched; repeatable
  --skip-unmatched      leave unmatched food lines out of the request instead
                        of refusing
  --purchase-date YYYY-MM-DD
                        required when the receipt itself has none
  --dry-run             show what would be sent; send nothing

connection and output:
  --url URL             Kyokki base URL, e.g. http://kyokki.lan:17300
                        (default: $KYOKKI_URL)
  --token TOKEN         API token, sent as a Bearer header and never printed
                        (default: $KYOKKI_TOKEN)
  --json                print JSON: the API's answer, or an error's detail
                        object (the default when stdout is not a terminal)
  --verbose             log each request and its status to stderr

examples:
  kyokki receipt confirm 0b6f7a3e-8d4c-4a53-9d1e-2f6c1b7e9a01 --all-matched
  kyokki receipt confirm 0b6f7a3e-8d4c-4a53-9d1e-2f6c1b7e9a01 --all-matched --assign 1=0b6f7a3e-8d4c-4a53-9d1e-2f6c1b7e9a01 --new 2=pantry
  kyokki receipt confirm 0b6f7a3e-8d4c-4a53-9d1e-2f6c1b7e9a01 --all-matched --skip-unmatched

exit codes:
  0 ok
  1 error: cannot reach the server, a 5xx, an answer that is not JSON, or a
    change sent that got no answer (it may have been applied)
  2 usage: bad arguments, or the receipt has no purchase date and --purchase-
    date was not given, an --assign/--new line is unknown, non-food or named
    twice, or the API rejected the request (400 invalid, 422; also a retried
    confirm's stale item, since confirm has no Idempotency-Key)
  3 not found: no receipt has the ID
  4 ambiguous name: does not occur for this command
  5 insufficient stock: does not occur for this command
  6 conflict: unmatched food lines without --assign/--new/--skip-unmatched, a
    receipt not ready to confirm (still processing, failed, or already
    confirmed), or a retried confirm that already succeeded (409)
  7 auth: missing or unknown token (401), or a read token on a write (403)
